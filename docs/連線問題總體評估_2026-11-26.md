# 板子連線不穩：總體評估與建議（2026-11-26 01:30）

## 1. 現象與已確認的原因

| # | 原因 | 證據 | 狀態 |
|---|---|---|---|
| A | **伺服器監聽 socket 死掉**：Windows asyncio Proactor 在 accept 時遇到 `WinError 64`（網路名稱已無法使用），行程還在但不再接受連線；8000 與 3000 都發生 | `fe-hub5\srv.err` 的 `Accept failed on a socket`；port 8000／3000 無 Listen；板子剛好每 60 秒重開 | 重開伺服器後 3 分鐘：0 次重開、ping 0 掉包 |
| B | **熱點本身會停頓**：筆電 Wi-Fi 同時連家裡 AP（2.4 GHz 通道 4）又開熱點 6267（通道 11），同一顆無線電來回切換 | 四台 ping **同時**掉包（7/92、6/56）；板子 IP 一晚換了三次 | 未處理；推測 A 的 WinError 64 就是熱點介面抖動觸發 |
| C | **2F 路口代號**：舊基底伺服器只回 `J(i,j)`，2F 板子收不到自己的路口 | 序列埠 `OLEDs 0/2` | 已修；GitHub main 早在 a0479ba（11-18）就正確，是我們用了較舊的基底 |
| D | **伺服器被回報量拖慢**：鏡頭牆開著時每台每秒 15–22 次，每筆都重算＋推送 | 組員 d7be3cf 的壓力測試 | GitHub 版已節流（每秒推 5 次、WS 0.5 秒逾時）；我們本機實測 CPU 14%、回應 28 ms，4 台時不是主因，8 台才會明顯 |

## 2. 韌體設計放大了問題

- 每 200 ms 開一條新的 TCP（`Connection: close`），4 台＝每秒 20 次連線握手；熱點一停頓就整批失敗。
- 回應只等 500 ms，且必須收齊本板全部路口才算「有回應」，回應稍慢或被截斷就不算。
- 60 秒沒有完整回應就 `sys_reset`；重開要約 20 秒（鏡頭＋模型），等於把短暫網路問題放大成每分鐘斷 20 秒。
- 真正卡死（405B 主迴圈卡住、33C1 序列埠全無輸出）時軟體看門狗不會跑，救不回來。

## 3. 和 HUB-8735（AmebaPro2 4.0.15）官方範例比較

| 項目 | 官方範例 | 我們 |
|---|---|---|
| Wi-Fi 連線 | `ConnectToWiFi`、`ObjectDetectionLoop`：setup 裡 `while (status != WL_CONNECTED)` 重試，之後不處理斷線 | FW 2.5 起加了斷線重連、60 秒重開（比官方完整） |
| HTTP 上傳 | `SimpleHttpRequest`：一次性 GET、`Connection: close`；`Capture_Image_HTTP_Post..._FASTAPI`：對 FastAPI 伺服器 POST、`Connection: keep-alive`，只在觸發時送 | 每 200 ms 輪詢一次，每次新連線 → 頻率遠高於任何官方範例 |
| 等回應 | `while (client.available())` 讀到沒有資料為止 | 固定 500 ms 視窗 |
| 當機保護 | `Watchdog/SimpleWDT`：硬體 WDT，`wdt.init(5000)` → `start()` → 迴圈裡 `refresh()`，卡住就硬體重開 | 只有軟體計時的 `sys_reset`，主迴圈卡住時不會觸發 |
| 持續連線的做法 | `MQTTClient` 範例（MQTT_Basic、MQTT_Image）：一條長連線、伺服器推送 | 沒用 |
| 偵測迴圈 | `ObjectDetectionLoop`：`getResult()` 後 `delay(100)` | 相同做法 |

結論：官方範例沒有我們這種「多台、高頻、雙向」的情境，網路穩定度要靠我們自己；官方提供但我們還沒用的是**硬體看門狗**和**長連線（keep-alive／MQTT）**。

## 4.5 01:40 更新：已做與實測

- 伺服器改用 SelectorEventLoop 後觀察 5 分鐘：三台序列埠 link lost 0、重開 0；四台 ping 共掉 1/380；無 WinError 64。
- **更正 B**：熱點不是和家裡 AP 用不同通道，而是**跟著家裡 AP 的通道走**（16:36 通道 11、01:23 通道 4）。家裡 AP 自動換通道時熱點被拖著一起換 → 全部板子斷線、IP 改變、伺服器出現 WinError 64。
- 乙太網路（192.168.1.10）沒有對外連線，筆電上網只靠家裡 Wi-Fi，所以「斷開家裡 AP」不可行。使用者決定先繼續用筆電熱點。

## 5. 建議方案（依優先順序）

1. **網路（最優先，效果最大）**：改用一台獨立的 2.4 GHz 無線路由器給 8 台板子，筆電用網路線或 Wi-Fi 接這台路由器，在路由器上為每台 MAC 綁固定 IP。不再用 Windows 行動熱點（會共用無線電、沒裝置時自動關、IP 一直換）。
   - 過渡做法：筆電 Wi-Fi 先斷開家裡 AP、只走乙太網路，讓熱點獨佔無線電。
2. **伺服器（必做，改動小）**：`server.py` 在 `uvicorn.run` 前改用 `asyncio.WindowsSelectorEventLoopPolicy()`，避開 Proactor 的 accept 問題；外層再加看門狗（`%TEMP%\fe-hub5\keepalive.ps1`）每 10 秒確認 8000／3000 有在聽，掉了就重開。
3. **韌體（下一版，交 hub-node-9）**：
   - 回應改成依 `Content-Length` 讀完（或最多 1.5 秒），收到任何 HTTP 200 就算伺服器活著；「路口沒收齊」只影響顯示、不影響看門狗。
   - 軟體重開門檻 60 → 180 秒，且只在 Wi-Fi 也有問題時才重開。
   - 加官方硬體 WDT（`WDT.h`，約 10 秒，迴圈裡 `refresh()`），處理主迴圈真正卡死。
   - 評估 HTTP keep-alive（同一條連線重複用），減少每秒握手次數。
   - 補回板上 LED 閃燈；版號跟組員統一。
4. **流程**：GitHub main 當唯一基底，hub-node-9 的分支先 rebase 到 main 再改，避免再出現 C 這種「修過又壞」的情況。

## 6. 擴充到 8 台鏡頭＋網路來源改成手機熱點（02:00 評估）

**流量與負載（實測 4 台推算）**：每台每秒 5 次回報（請求約 0.2 KB、回應 291 B）＋鏡頭牆每秒 1 張 JPEG（約 15 KB）→ 8 台合計約 1.2 Mbps、每秒 40 次新連線；伺服器 4 台時 CPU 11%，8 台約 20–25%（組員 8 台×每秒 20 筆的壓力測試 0 逾時）。頻寬與伺服器都夠。

**卡關點**：
1. **Windows 行動熱點最多 8 個裝置**：8 台板子剛好塞滿，沒有空間給中控台以外的手機（避難人員頁面）、組員筆電；第 9 個裝置連不上，或擠掉別人。
2. **熱點跟著筆電連的上游 Wi-Fi 走同一通道**：上游換成手機熱點後，手機熱點換通道、手機鎖屏省電關熱點、來電或移動，都會讓筆電熱點一起斷 → 8 台全斷。iPhone 熱點沒人用時會自動關、Android 有閒置逾時。
3. **板子直接連手機熱點也不行**：韌體裡伺服器 IP 寫死 `192.168.137.1`（secrets.h），手機熱點網段不同 → 要重燒 8 台；手機熱點同時連線數也有限（iPhone 約 5、Android 約 8–10）。

**建議**：
- **正式做法**：一台獨立 2.4 GHz 小路由器（旅行路由器即可）專給板子：SSID／密碼設成和現在一樣（6267）、LAN 設 192.168.137.0/24、筆電用網路線接並固定 192.168.137.1 → **8 台韌體都不用改**；固定通道、DHCP 綁 MAC、可接 20 台以上。筆電上網走手機（USB 網路共用或 Wi-Fi 都可），和板子網路完全分開，手機熱點斷了不影響展示。
- **不買設備的過渡做法**：手機改用 **USB 網路共用**給筆電上網，Windows 熱點從這條 USB 連線分享 → 筆電無線網卡只當熱點，通道自己固定，不再被上游拖著換。8 台上限仍在。
- 展示現場本身不需要網際網路；只要伺服器在筆電上，板子和中控台都能跑。
## 7. 02:00 新發現：鏡頭牆開著時板子卡死

- 01:33–01:50 中控台沒開（沒有快照要求）：四台 0 重開、0 斷線。
- 01:55 開中控台、鏡頭牆在畫面上（每台每 0.5 秒上傳一張約 15 KB 的 JPEG）→ 約 10 分鐘內 405B、0280、436B 的序列埠**完全沒有輸出**、ping 不通，33C1 正常。軟體看門狗（60 秒 sys_reset）也沒觸發 → 主迴圈卡在某個呼叫裡沒回來。
- 推測位置：`httpPost` 的 `client.write(data, 15 KB)`（熱點一頓時 TCP 送不出去，WiFiClient 沒有送出逾時，會一直等），或 `Camera.getImage(CH_JPG)`。今天稍早 33C1、405B「整台無輸出」也都發生在鏡頭牆開著時。
- 修法（交系統程式）：
  1. 官方硬體看門狗 `WDT.h`（`Watchdog/SimpleWDT` 範例）：約 10 秒、迴圈裡 `refresh()`，任何卡死都會硬體重開。
  2. 快照分段送（例如每次 1460 bytes），每段檢查時間，超過 2 秒就放棄這張。
  3. 鏡頭牆預設不開即時更新，或快照降到每 2 秒一張。
- 驗證：`flash_tools/watch.ps1 -Seconds 1800` 期間鏡頭牆一直開著，0 卡死。
- SDK 佐證（AmebaPro2 4.0.15 `WiFi/src/WiFiClient.cpp`）：`write()` 直接呼叫 `clientdrv.sendData()`，socket 預設阻塞，只有 `setRecvTimeout()`、沒有送出逾時 → 對方不回 ACK 時 `write` 會無限期等。可用 `setNonBlockingMode()` 配合自己的逾時，或靠硬體 WDT 兜底。
