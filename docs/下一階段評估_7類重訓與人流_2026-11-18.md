# 下一階段評估：7 類重訓（加人偶）與人流計數（2026-11-18）

## 結論

**目標（使用者確認）：模型要能辨識人偶（類別 6 = person），作為人流計數的基礎。** 所以 7 類重訓是下一階段的必要項目，不是選配。

- **7 類重訓：可行。** 資料（3,400 張渲染、標註錯誤 0）和 Colab 筆記本都已備妥，T4 跑 80 輪約 1.5～2.5 小時。
  - 但照現在的資料訓練，很可能重演 6 類模型的問題：合成驗證集分數漂亮，實景誤判嚴重。
  - **開訓前先修下面 A1～A3，實景照片是最關鍵的一項。**
- **人流計數：可行，但建議改成伺服器端追蹤。** 現在的 `people_flow` 是一支獨立韌體，和 `hub_node` 不能同時跑。
  - 板子本來就把所有偵測框送到伺服器，在伺服器端追蹤就不用改韌體。
  - 伺服器端有 8 台鏡頭的資料和地板座標，可以避免同一個人偶被重複計數，也能跨樓層統計。

> **2026-11-18 小規模補訓結果**（420 張渲染圖、40 輪，詳見 `retrain/experiments/small7_results/README.md`）：
> - 人偶 AP@0.5 0.92，框高 ≥ 30 px 時召回率 77～91%，**加人偶可行**。
> - 煙（0.002）和瓦礫（0.24）幾乎學不到，原因是渲染資料：煙的可見判定被雜訊撐大，標到看不見的煙；瓦礫被渲成一團白。
> - 正式重訓前要先修 `dr_render.py`（R1～R3），並補遠處小人偶（R4）。

## B. 人流計數

**能不能看到人偶**（`people_flow/README.md` 的估算）：
- 40 mm 人偶在鏡頭附近約 30～55 px 寬，房間另一側約 13 px。
- 近半邊夠 YOLOv7-tiny 偵測，遠半邊交給對面的鏡頭。
- 人偶是手動拖動的，速度慢；板子約每 150～200 ms 回報一次，追蹤跟得上。

**建議架構：在伺服器端追蹤**

| | 板上追蹤（現在的 `people_flow` 韌體） | 伺服器端追蹤（建議） |
|---|---|---|
| 韌體 | 要把 `PeopleFlow.h` 併進 `hub_node`，兩支程式合一，再重新驗證 OLED、Wi-Fi | 不用改，`hub_node` 已送出全部偵測框 |
| 重複計數 | 每台用畫面裡的 A/B 區，4 台視野重疊，要靠劃區避免重複 | 先投影到地板座標（`evac.unproject` 已有），8 台合併後再追蹤，同一個人偶只算一次 |
| 計數線 | 依畫面方向劃，閘門一改就要重劃 | 直接用走廊段、出口、樓梯當計數線 |
| 用途 | 只有人數 | 每段走廊的人數可以給路徑規劃當壅塞權重，中控台也能顯示 |

做法：
1. 把 `PeopleFlow.h` 的配對、確認、保留、計數規則改寫成 Python（約 200 行），單位從畫面像素換成 mm。
2. 用 `people_flow/test/sim_test.cpp` 的同一組情境做 Python 版的回歸測試。
3. 中控台加「各走廊人數／出口累計」。

本次已先做的一步：`evac.fuse()` 收到類別 6（人偶）不會再把它當障礙物，不認得的類別也會略過（原本會 IndexError 當掉）。

## C. 建議順序

1. 桌上實測 Wire1（`oled_fw/README.md`），在有 SDK 的電腦上完整編譯 `hub_node`。
2. 閘門 94 mm 同步回實體模型（A1），補 2F 渲染（A2）。
3. 實體模型回來：裝鏡頭、受控測試舊模型（記錄每類誤判率，當基準），同時拍實景照片（A3）。
4. Colab 訓練 7 類 → 實拍測試集評估 → 轉檔（A4、A5）→ 上板。
5. 伺服器端人流追蹤（B），用磁鐵拖人偶做人工計數加錄影對照。
